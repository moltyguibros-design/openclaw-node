STAGE1 IDENTITY PROFILE BINDING — design candidate v1 (D312)
Baseline: PR #224, f4135e094ed2c950e6858598c087e6c141290701.
Scope: ONE design outcome under D168/D261. This companion controls the identity-provenance ambiguity in launch proposal v6 sections 2/4 only. The historical v6 file and all executable/CI bytes remain unchanged. No production command, profile values, installed authority or identity adapter is provided.

1. Selected approval binding
Place BOTH operator and capture identity policy inside the per-host runtime-profile file already named by launch v6's FOUR-binding bootstrap. Do not introduce a fifth identity file/digest. The approved runtime-profile SHA256 covers the entire exact profile, including its mandatory identity_policy section, runtime components and startup-environment policy. A profile approved without identities is not upgraded by filling them later. Any changed identity, account evidence, runtime or environment requires a newly reviewed complete profile and new independent approval of its whole-file digest. Existing approval never authorizes automatic refresh.
The other three bootstrap bindings remain Stage0 artifact, installer and installer manifest release constants, obtained from independent exact-source reviewer recomputation as v6 requires. The application program-release manifest retains its existing separate release comparison; it is not silently counted as, or substituted for, this per-host profile. No existing manifest schema or digest changes here. No actual complete per-host runtime-profile schema/consumer currently exists.
Why this choice: one approved byte string binds identity and runtime selection together and avoids separately approved identity/runtime documents being mixed across hosts or revisions. A fifth binding could work only with additional cross-binding and lifecycle rules; it is not selected. A hash establishes byte equality to the independently approved selection, not the selection's correctness or who approved it.

2. Provenance of approved identity data
A future strict, versioned runtime-profile schema MUST require one identity_policy section containing distinct positive operator_uid and capture_uid, the target host/platform binding, and separately identified operator/capture deployment-account evidence bindings. UID fields are JSON integers (not bool, string, floating point or a sentinel), within the selected platform's separately reviewed supported range. Missing, zero, equal, unknown, unclassified or out-of-range roles refuse. No default 501, runner uid, argv-derived value or fallback field exists. The final exact schema, native host/account mapping and numeric ranges are a later adapter-contract prerequisite, not invented by an observation.
The expected operator/capture identities originate in separately reviewed deployment/account records for that exact host, obtained by the trusted operator in the protected context/channel specified in v6. Bind those exact reviewed record bytes by SHA256 in the complete profile; the independent approval record names their provenance, immutable review references and the host/role assignment. Account names alone, a copied uid, Git authorship, a signature alone, agent observations or a caller-created self-consistent record do not establish approval. Unknown source or unavailable reviewed record blocks profile approval. This is a normative future input contract: no actual records, host identification or approval is supplied here.
The trusted operator approves the complete runtime profile and its digest in that protected channel independently of the capture principal and author-supplied values. The protected phase-authorization record binds the exact profile path/digest, host, approved release, allowed phase and its independently specified validity/recheck conditions. It must identify the independent profile approval and account-record review, not merely repeat an author digest. The profile cannot carry an authoritative digest of itself or certify its own approval. The operator/channel and existing root administrators remain trusted; this is no defense against their compromise.
Expected policy identities are stable approval data; actual kernel/login/session observations are per-phase evidence. Do not copy a current SUDO_UID, loginuid, audit uid, session id or CI report into the expected role to make a comparison pass. UID/account reuse, host mismatch or account-record drift must invalidate the phase selection and require newly reviewed approval; old profile approval alone never establishes a current account or protected session. The concrete account/host observation method and bounds must be specified and tested in the later adapter contract before any launch, with unknown/drift refusing.

3. Approval before interpretation and use
Before role values or runtime selections influence a launch, the trusted pre-start Stage0 path compares the bounded regular protected profile FILE's exact bytes with the independently expected whole-file digest. A path is only a locator, not authority. Then validate the entire strict versioned schema, exact fields/component set and identity_policy; reject duplicates, unknown/extra/missing fields and noncanonical encodings under the later reviewed schema. Only then interpret policy values. Bounded inert byte acquisition/lexical parsing is not execution of profile content. No shell evaluation, interpolated command text, dynamic imports or executable profile fields are allowed.
Stage0 performs its existing pre-start checks without sudo in the protected administrator context, after authenticating Stage0 externally as v6 specifies. Failure or unreadability has no root fallback. The later independently authenticated Stage1/window consumer MUST independently verify the same expected profile binding and use one held, approved immutable byte snapshot across policy interpretation and use. A self-rehash against a caller digest is not independent approval. Held/path mapping or relevant metadata drift refuses; do not reopen a new profile after checking one and consume the replacement. Root-only/trusted-operator-only modifiability across the verification/authentication gap remains v6's stated trust assumption, not a claim of physical exclusion of trusted updaters.
Every phase must select the exact protected approval, current host/account observations and approved runtime/environment policy before policy publication, challenge generation, image access or a usable receipt. No mutable current symlink, implicit latest profile, automatic downgrade, runtime-selected expected uid or optional identity field is admitted. A path/digest passed as data must be equal to the independently selected protected authorization; it does not become authority just because it is on argv. A caller may propose data, never choose the expected digest or role values for an admission decision.

4. Independent actual identity and unresolved native limits
Expected operator_uid comes from the approved profile. Actual SUDO_UID is observed from the fixed authenticated sudo launch's startup environment before replacement, never supplied as authority by the caller. The later adapter must cross-check it against independently kernel-derived audit/login identity and the approved operator role, require capture_uid to differ, and apply the reviewed root credential/environment/runtime checks. Missing, malformed, sentinel, unavailable or mismatched identity refuses; there is no selectable weaker fallback. SUDO metadata plus matching kernel fields is consistency, not by itself proof of a protected session. V6's protected session-entry/configuration admission and per-phase authorization remain separate mandatory gates.
D309/D311 observations are hosted-runner evidence only: Linux loginuid/sessionid unset supplies no native positive; Darwin auid equals runner/capture in the old model supplies no distinct-operator positive. Masks remain privilege-filtered metadata under D310's reference-only C1 interpretation. Current CI key sets, launcher paths and interpreter versions are not approved profile values. The old anchor's argv/default-SUDO_UID assumption and CI wrappers remain unchanged CI-only behavior; no existing entry is relabelled the new adapter.
R7 stays OPEN. Darwin saved uid was unavailable in the recorded observation; this design supplies no equivalent API, waiver, synthetic saved uid or acceptance of unknown state. Before an adapter implementation, a separate immutable reviewed contract must decide the supported credential checks and their limits for each platform, including whether Darwin can meet them. If no supported independently justified check exists, that platform stays ineligible. Native-positive fixture eligibility is also unresolved: require an actual distinct-operator, distinct-capture, supported native identity context on fresh disposable CI, with full bounded recording and honest refusal controls. A mocked provider may test logic only. No audit/login setter, account/session change, runner result manufacture or repeated host probe is authorized to produce a positive here.

5. Design verification and next consumer
Independent immutable review must verify: all expected identities are covered by the one independently approved complete profile; digest/schema precede semantic use; profile replacement/mixed-host/account drift/unknown approval and caller-selected digests cannot become authority; old CI assumptions remain excluded; R7 and actual host/session/runtime approval stay open. Review the refusal matrix below as design obligations, not executed tests:
- Correct approved whole profile plus separately authenticated matching observations: eligible to continue only after every OTHER phase gate, not production admission from this design.
- Self-consistent rewritten profile and supplied digest, or appended/omitted identity fields: refuse without independent whole-profile approval and strict schema.
- Mix approved runtime A with identities/account records from B, stale host/account evidence, equal roles or current observations substituted for expectations: refuse.
- Valid digest of one profile followed by selection/use replacement, unknown schema or unrecognized field/range/platform: refuse before policy/image/receipt side effects.
- Missing/invalid sudo metadata, unset/mismatched native identity or unsupported saved-uid/native-positive method: no accepted native launch; retain the gate.
Feeds: the later Stage1/window adapter CONTRACT, which must specify the exact strict profile schema, protected approval selection/retention, bounded host/account/native credential observation, platform saved-uid policy, native-positive fixture class, whole-action held binding, rejection-before-side-effect tests and intended-assertion mutants. Only a separately reviewed bounded source/test unit may implement that contract. Completing this provenance design closes only the R2 design choice, never R7 or implementation/readiness.
