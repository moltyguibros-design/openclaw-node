PROTECTED ACCEPTANCE LAUNCH DESIGN — proposal v6
Baseline: PR #224, 794ad739b6854b74a3a30cb2279b28630d38968e.
Scope: design only. This replaces v1/v2/v3/v4/v5 as the current proposal. It closes no inventory row and certifies no installed program, host authority, B3 provenance, B8 acceptance, D62 decision or operational readiness. No code, workflow, ledger, VERSION, account, permission, service, VM or image is changed.

1. Trust boundary and unresolved access
D261's interactive-root model remains selected, not a single privileged call per window. Every privileged phase needs separately scoped attended authorization, fresh authentication and credential invalidation. No daemon, sudoers grant, persistent helper or unattended session is proposed.
The proposed authority requires a distinct trusted administrator uid and protected login/session/home/terminal inaccessible to the capture principal and agents. It ALSO requires the bounded configuration-admission result below for the actual capture uid. A separate admin does not establish that result. Actual satisfaction remains unknown and production authority is refused. Creating accounts, removing rights, moving runbooks or modifying authorization is not authorized here.
The admission claim is only: no configured elevation route was observed in a declared, completed observation set at the recorded time. It is NOT an exhaustive proof that the capture uid can never become root. A separately authorized READ-ONLY PRIVILEGED host-access assessment, using a fixed reviewed OS-tool observation sheet from the protected operator context, must precede installation admission. It does not run a candidate runtime, alter rights or collect early B3 pins. Declare host identity, exact inventory roots/queries, include traversal rules, enumerated endpoints, maximum depth/count/bytes/time and stop conditions before running it. A bound, unreadable entry, missing include, unclassified endpoint/argument/config or incomplete enumeration is unresolved and refuses admission, not an empty result.
The observation set includes account/group memberships; sudoers and all declared includes; applicable authorization-database rules; configured privileged helpers and their caller/operation policy for the capture uid; root-domain loaded and on-disk launchd jobs/helpers, including their programs, interpreter/wrapper targets, plists, startup/config/PATH dependencies; capture-writable setuid/setgid files in the declared roots; root cron/periodic/emond entries; and capture-writable root-run startup/search paths. Include known vendor/Homebrew/app-bundle routes rather than treating a signature or root-owned wrapper as proof of downstream ownership. These are ACTUAL TARGET HOST observations; a guest D60 example is only a motivating class, not host proof.
The SAME bounded observation set must also cover routes into the protected OPERATOR SESSION, not only routes directly to root: global LaunchAgents/login items and their executable/config/interpreter dependencies; system-wide shell startup and /etc/paths.d entries/search targets; PAM/authorization plugins, input methods and other bundles loaded into that session; operator home/startup files and terminal profiles; and applicable session-control/automation routes. Capture-writable or unclassified operator-session inputs refuse admission under the same bounds, recording and per-phase recheck rules. No operator-session or host state is currently admitted. The session-entry procedure and its approved platform profile must themselves avoid known capture-writable startup routes; unknown safe entry remains a gate rather than a reason to run a candidate in that session.
The read-only privileged recheck is a declared PART of EACH phase's authorization, with the same set, bounds and recording, not an unacknowledged recursive authorization step.
Admission requires a complete declared set with no admin-group/sudoers/authorization grant permitting capture-principal elevation, no observed capture-writable root executable/config/ancestor or delegated root operation, and no unresolved applicable helper or route. Platform/vendor components require an explicit approved profile and policy classification; unknown is not implicitly trusted. Recheck this same declared set before EACH later privileged phase and refuse on drift, truncation or uncertainty. Preserve exact query argv, bounds, statuses, times and normalized results in protected evidence. Residuals include unenumerated routes, unknown local privilege-escalation bugs, flawed vendor helpers, prior compromise and changes outside the observed interval; carry these limits into B6. This is a bounded policy/configuration admission, not complete physical exclusion or a clean-host certificate.
A terminal emulator or browser inside capture uid501's GUI session does not qualify merely because su/login selects another uid. The operator must use a separate protected GUI login, console or another device. Passwords are never collected, typed or handled in agent-controlled contexts. All other attended elevation procedures would need to use that protected context too.
The approval channel is part of the boundary: the review record, Stage0 sheet, exact digests and runtime approvals must be obtained and compared there or on another trusted device, not through uid501's browser/terminal. Root administrators and that independent operator/channel remain trusted. We claim no independence from an already privileged attacker.

2. Bootstrap artifacts and constants
Propose a separate reviewed installer artifact plus its manifest, and a short fixed Stage0 command sheet using only trusted absolute OS tools. Bootstrap uses FOUR independently approved SHA-256 bindings: the Stage0 artifact itself, installer, installer manifest, and per-host runtime profile. The first three are release constants; the fourth is per-host approved data. Each release constant enters the protected approval record only from the independent exact-source reviewer's OWN recomputation from the immutable reviewed commit, retrieved independently of the author-supplied artifact/ledger, or after a recorded equality check against that recomputation. The independent review report must name the immutable commit, exact artifact paths/bytes and the recomputed values. Protected display alone does not establish who chose the digests; author-provided hashes and self-consistent artifacts are not approval. The same rule applies to the approved program-release manifest digest consumed by the first source unit. The per-host runtime-profile digest instead comes from the operator's approved profile produced in the protected context. No such reviewer recomputation or real profile is claimed for these unimplemented future artifacts. Stage0's own expected digest exists only in the protected approval record, not embedded in the artifact whose bytes it authenticates; there is no self-hash cycle. Verify the runtime-profile FILE's own digest and strict schema/declared component set BEFORE interpreting any of its contents. A substituted, omitted, expanded or self-consistently rewritten unapproved profile refuses. Stage0 copies inert installer/manifest data into exclusive root-only staging and Stage1 runs only the verified root copy. No copied application/installer code decides whether it is trusted.
Release constants are the Stage0 artifact digest, installer digest, installer-manifest digest, exact installer file set/schema, and destination-layout rules. Per-host data are explicit source/staging paths, the approved runtime-profile path/digest and operator/capture identity profile. These are data, never substituted shell/code text or evaluated commands. Unknown or extra parameters refuse.
Before ANY Stage0 script text runs, one minimal literal trusted /usr/bin/env -i /usr/bin/shasum -a 256 -- invocation hashes the regular protected Stage0 copy; the operator compares that result to the Stage0 digest obtained independently in the protected channel. This minimal command/constant comparison, not Stage0, authenticates Stage0. It is a procedural operator control, not a new unverified helper. Source preparation and the protected copy must be inaccessible to the capture principal, with no links, startup-file injection or mutable capture-controlled approval channel. Only after that comparison may the fixed absolute no-startup-file shell run the verified protected copy with its explicitly validated parameters and clean environment. The hash-to-exec gap relies on that protected copy being writable only by the trusted operator or root, under the same short-gap trust assumption as runtime verification; it is not physical exclusion of a trusted updater. Put that shell and the minimal OS verification tools in the sealed-system trust/evidence class. CI must verify the same Stage0 bytes against the same release binding before executing them; CI's approval values remain fixture data, not a real operator-approval certificate. No unauthenticated Stage0 source is executed from the checkout. This is the future artifact contract, not an issued command sheet or authorization to run one.
The Stage0 artifact includes the full reviewed, tested looping/verification logic for every declared component and ancestor; it is not described as a few informal commands. Its parameter syntax requires absolute literal paths, restricted characters and always-quoted data expansion, never eval.
The SAME Stage0 command text and installer bytes are exercised in disposable CI. Only the declared parameter values differ using a recorded, reviewed fixture parameter set. CI approval parameters are test fixtures, not evidence of real operator approval. A real invocation record must resolve every value and bind both release constants and per-host profile approvals; 'no unresolved placeholders' applies to that record, not to the existence of declared parameters in the fixed command text.
Initial installer/manifest sources must already be regular, bounded files in the protected operator's staging area, not capture-writable sources. Preparing them is an unprivileged inert data-copy step. Stage0 source reads must have tested size/type/time limits; plain unbounded cp is not the specification. Application payloads later copied by the verified installer may remain capture-writable inert data: they must produce exactly approved bytes or refuse. No raw failed input or secret file content is exposed to the capture principal.
The installer/Stage0 artifacts have their own explicit source/test contract BEFORE any CI demonstration. No such artifact or executable command sheet is claimed implemented in this proposal; this is not installation instructions.

3. Pre-start runtime trust
Host characterization precedes any installation proposal. It is separately bounded, unprivileged and inert, performed in the protected administrator context without sudo. Agent/uid501-produced characterization is untrusted input, not approval. Existing production state/image/holder guards apply. No candidate runs as root to vouch for itself.
Forbid dispatcher/shim/wrapper launch targets. Establish the exact final executable and re-exec/framework chain with trusted OS metadata/signature/hash observations. Record full-path owner/mode/ACL/flags, identities, architecture/version and lifecycle status. CI's Python3.9 is not host approval. If static evidence cannot establish a dependency, leave it unresolved and refuse privileged startup; a later unprivileged execution characterization is a separate reviewed step, not called inert.
Use two evidence classes. Sealed system components require BOTH OS build (including any security-response suffix) AND approved shared-cache identity/UUID, together with measured SIP/authenticated-root/SSV state, not a demand for nonexistent separate dylib files. Data-volume executables, frameworks, standard-library/extensions and native tools require approved file hashes and full-path/ACL/flags checks. Apple's shared-cache and SSV documentation support this distinction; no corresponding host measurement is claimed.
Stage0's runtime-profile digest check, schema/component checks and full component/ancestor verification run as the protected administrator WITHOUT sudo, using the trusted OS-tool Stage0 artifact immediately before the separately authenticated root Stage1 phase. This selected contract requires the runtime/profile inputs to be readable for that unprivileged verification; unreadable or inaccessible inputs refuse, with no automatic root fallback. Inert root-owned installer-copy/hash actions remain separately authorized OS-tool steps. Root-only component modifiability is the stated trust assumption across the short verification/authentication/exec gap, not proof that no trusted root updater can act. Later window launches use the SAME approved-profile pre-start verification, with drift refusal before image work; post-start checks are additional and do not replace it. Every profile approval and observation is bound to the particular phase; an old characterization alone never admits a launch.
Owned proof must compare kernel-reported actual executable/loaded components with the pre-approved profile, using the appropriate system-cache or file class. Post-start observations do not establish pre-start trust. Unknown, changed, unreadable or unclassified components refuse before image use. No runtime is currently selected or certified.

4. Authenticated identity and environment order
Clear inherited startup-influencing environment in the protected operator context BEFORE invoking trusted sudo; sudo then creates its own metadata. Do not insert env -i between sudo and the verified program. The future verified program observes sudo-set SUDO_UID before replacing its own environment; it is never typed or supplied on argv as authority. Cross-check it with a kernel-derived audit-session/login uid and the policy's distinct operator uid; unknown/unavailable or mismatched kernel identity refuses. The capture uid is a SEPARATE policy field and must differ from that operator uid.
Stage0, consisting only of literal OS commands, enforces protected-session provenance procedurally, not mechanically. Stage1/window adapters must implement and test the mechanical identity check before accepting policy or image work. The current CI entry's SUDO_UID==capture-uid assumption and argv fallback are NOT production validation and are not silently reused; a separate future adapter contract is required.
Record the exact post-sudo startup environment key set in the approved launch profile and refuse unknown or startup-influencing keys before the selected invocation can be admitted. The root-controlled sudoers env_reset/env_keep/secure_path and exact fixed pre-sudo launch are part of the PRE-START profile, not an inferred property of env-i or a post-start repair. The program's later key-set check detects drift only. Only explicitly authenticated metadata may survive startup. The program then installs its exact allow-listed environment, cwd/, isolated Python, no site processing/bytecode writes and a protected absent bytecode prefix. No inherited Python/DYLD/caller import search is accepted. This identity/environment work is not folded into the first source unit.

5. Protected layout and publication
The proposed records path remains /private/var/db/openclaw-recovery/acceptance, directories0700 and records0600. A proposed code path is /private/var/db/openclaw-recovery/programs/<approved-release-manifest-sha256>, root-owned0700 with0600 source files. Neither path is installed or newly approved by this document.
Keep the manifest outside the existing exact twelve-module directory. Refuse source links/unexpected files, destination replacement, granting ACLs or capture-writable executable ancestors. Hold/check path mappings and bounds, fsync files/directories, use truly exclusive atomic publication (RENAME_EXCL or verified equivalent), sync its parent and never overwrite a release. Ordinary replacing rename is insufficient. Failed staging remains explicitly unusable and size-bounded; no retry, fallback/current symlink or automatic cleanup.
The complete initial installer, runtime and literal Stage0 artifact have separate approvals. Checking program ownership after importing a writable program cannot establish startup trust.

6. Window input provenance and order
Operator-supplied: authorized host/VM/capture principal, allowed paths, approved release/runtime digests and expected guest/protected-writer uids from separately reviewed deployment/account records. Unknown source or unaccepted limits refuse. Do not derive expected guest owners from the capture or mount a live image to obtain them. Pre-stop owner preflight observes host-side context only.
Root-observed: actual just-in-time B3 plist/config/role bytes and metadata. Their source may remain capture-writable. A seal proves only what root observed at seal time, not authorship, correctness or continuity until stop. B6 must explicitly name this residual limit.
Root-generated: a fresh unpredictable window challenge and one-use authorization identity. A separate future arm/policy integration must bind that challenge through arm/commit/ACK/capture. Existing user-generated nonces are not relabelled root-generated; this integration does not exist merely because the proposal names it.
Order: protected unprivileged inert characterization; separately authorized read-only privileged host-access configuration assessment and complete bounded admission; separately authorized installation and owned-resource installation proof; separately authorized just-in-time read-only B3/host-context preflight; root policy seal after B3; separate fresh exact-window B6 release after B2/B3/B5 readiness; then B7 quiescence/stop and VM power-off with active boot denial; then post-capture attended root anchor/read; then distinct B8 acceptance OR complete host cleanup and D62 ABORT. Every root phase has its own scope/authentication/evidence. A seal does not grant B6 or attest an unknown future checkpoint. Source/installed readiness before B6 is distinct from later real-window observations. The heartbeat never initiates a production stop.
Journal/checkpoint evidence remains user-owned quiescence evidence. This design adds no physical exclusion proof for the last-NATS-stop-to-manifest interval and no root journal-close dependency.

7. Reader, B8 hand-off and failed-copy disposal
Reuse the existing anchor, reader_code and Q reader. Attach only the protected root-owned copy using the existing verified read-only mount/cleanup primitives. Capture, protected copy and record store must satisfy the actual same-APFS-filesystem requirement, not merely a shared container. All policy, byte, role, owner and identity mismatches or runtime/cleanup uncertainty refuse a usable receipt.
Preserve pending fences, exclusive publication, bounded records, fsync/read-back and primary-error retention. A semantic receipt is not B8 acceptance, D62 admission or boot permission. Q's successful cleanup removes its protected copy. Therefore root-receipt independence DOES NOT automatically carry into B8: B8 input binding remains a named OPEN contract requiring either a retained protected copy with its capacity charged or re-verification of anchored bytes through held descriptors. No choice, implementation or successful hand-off is claimed here.
Before real-window enablement, a separate reviewed/tested attended root-only protected disposal operation must exist. Failed-nonce reconciliation is ABORT-only: no re-read, reset, overwrite or reuse. Bind the trusted failure/pending record, exact clone/held parent and device/inode/birthtime where available; refuse links, missing trusted identity, drift or any source/production-image identity.
Measure the expected mount/attachment absence AND no remaining holders of the exact clone before treating disposal/reclaim as proven. Persist command/argv/scope/bounds/status/times and normalized observations, including refusals; D287/D288's recording gap cannot be repeated. Uncertain results retain denial. Preserve evidence separately and durably before unlinking only the exact verified disposable clone through its held parent; fsync and verify absence/result. No recursive cleanup or guessed eject/deletion target. Retained/open clones remain charged until absence/holder/disposal evidence supports release.
D62 may not publish usable ABORT or permit boot/admission while protected cleanup is unresolved. Identity/detachment uncertainty requires a separately attended manual incident contract with denial retained. New attempts need a new nonce and fresh admission/authority. Existing Q success cleanup is separate. No disposer or cleanup authority is supplied here.

8. First bounded source contract
Goal: add an independently digest-pinned approved-release comparison to the EXISTING common root entry path, before action-specific writes/image use or project dependency imports. Cover publish, verify, read and receipt, include host_capture_anchor.py itself, and preserve existing reader_code origin/FD/runtime controls. There is no second loader.
Needs: existing owned anchor/reader fixtures and baseline; a strict release-manifest schema and separately trusted expected-digest CALLER contract; inert local fixtures. No actual host approval or installation is implied by a test input.
Use ONE held approved-release context spanning each whole action. The common gate verifies canonical manifest bytes against the independently expected digest, opens the exact declared source set, captures bytes/hashes from held descriptors and checks their mappings against the approved manifest. reader_code must CONSUME THAT SAME held context and approved snapshots, not open a fresh self-comparing source set after entry. Recheck held/path mappings before loading and refuse measured swaps. Load/compile ONLY those exact already-approved byte snapshots in the existing loader. The anchor's own bytes are held and compared for drift, but its canonical name host_capture_anchor is NEVER IMPORTABLE: any import of it refuses, and no second anchor module object is created. It remains the already-running entry, authenticated by protected startup and passed explicitly to Q as a. Refuse a pre-existing canonical anchor alias when entering reader_code and recheck its absence before image use; use a fresh process for fixtures rather than accepting a preloaded test alias. Inside reader_code, use one held-context finder/loader for the OTHER ELEVEN declared project names, including TRANSITIVE imports, and a refusal for the anchor name. A normal pathname importer may not serve any name in the twelve-name set. Refuse other project names already present when reader_code starts; thereafter every permitted project import must resolve to the same module object proven loaded from THIS held approved context or refuse. A matching __file__ string alone is not provenance. Check module-object identity after loading and before image use, keep the finder for the whole action including lazy imports, compile snapshots with explicit filenames and no bytecode, and exercise these controls in fresh processes. Preserve the stated limit for the already-running anchor: its authentication came from protected startup, not this comparison. Inter-module imports, including host_guest_commit's host_vm_preflight/nats_identity/preservation_journal dependencies, must use the same snapshots. This extends reader_code in place, not a parallel reader or source tree. No unapproved executable source may be reopened by pathname. Preserve fixed module names/origins and runtime checks, and refuse mapped-file drift before any image operation or usable publication. The approved hashes recorded in receipts must correspond to the exact snapshots actually loaded.
Feeds: later installer/bootstrap contracts, not production enablement.
Verify: honest approved selection; a self-consistent unapproved code+manifest rewrite; altered expected digest; extra/missing modules; noncanonical/extra fields; bool/invalid sizes; stale release; and selection/use swaps. Include explicit swaps BETWEEN entry and reader_code, BETWEEN held hashing and actual module execution, and of a TRANSITIVELY IMPORTED module before its dependency import; add an intended-assertion mutant that removes the held-context import guard, plus refusal controls for a direct/transitive anchor import and preloaded canonical aliases; unapproved replacement code must never execute, and a measured mapping swap must refuse before the action side effect. EACH of four actions has refusal-before-side-effect controls and intended-assertion mutants for per-action bypass, held-context bypass and snapshot/import mismatch. Preserve CI/fixture/path/UUID barriers, including each new entrypoint; if the CI command shape changes, update its gate mutants accordingly. Later exact-source Claude review and all-eight fresh CI are required.
The comparer and already-running anchor are part of the compared set. This is drift/misinvocation detection, NOT authentication of its own executing code. Trust still originates in protected approval, Stage0/Stage1, root-only storage and pre-start verification. This unit adds no installer, identity adapter, window policy/challenge, B8 hand-off, disposer or production command.

9. Remaining sequence and limits
Separate later source/test contracts are required for installer+Stage0, operator/capture identity adapter and runtime proof, root challenge/policy binding, protected disposal, and B8 input binding before any real enablement. CI must execute the actual candidate artifacts on fresh disposable resources with distinct principals, honest controls, relevant negatives, interruption evidence and complete cleanup accounting. Tests model approval but cannot prove a real operator's independent approval. No local elevated/full-root or live-bus tests are authorized.
Only then consider an exact-host installation proposal naming access conditions, fully bound artifacts/profiles/paths, mutations, verification and attended reconciliation. Access/account changes and installation each need separate explicit authority; no permission follows from this design.
The disposable macOS D62/D175 reboot rehearsal still needs exact operator-designated access or a fixed disk/memory budget and capacity source. Recorded24.558GiB does not fund the320GiB planning candidate plus reserves. B5/1.2 and protected acceptance remain in flight; B6-B9 held, D64/Gate unchanged, production capture disabled. Claude131 withdrew its prior use of guest D60 and the October2 guest sudoers record as evidence about the physical host's uid501. They are motivating examples only; no host privilege claim is derived from them. This proposal remains pending review; no remaining design finding is preclaimed resolved. Claude133 closed X1 and all structural X2/X3 points except the Y1 independent-reviewer digest provenance and Y2 nonimportable running-anchor precision; v6 states those corrections without preclaiming their review.
